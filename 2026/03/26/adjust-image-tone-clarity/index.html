AI的SKILL是什么

2026-10-15

在日常使用 AI 编程助手或对话助手时，提示词（Prompt）、系统提示词（System Prompt）、Skill（技能） 和 MCP（Model Context Protocol，模型上下文协议） 这四个词经常出现，也经常被混淆。它们其实是四个不同层面的「输入」与「能力」，层层配合，共同决定了一个 AI 助手到底做什么、怎么想、怎么干。

1. 提示词（Prompt）

提示词是你在每一轮对话里输入的那段文字，是面向当前任务的最直接指令。它告诉模型「这一次要做什么」，生命周期最短、最具体，每一轮都可能完全不同。

2. 系统提示词（System Prompt）

系统提示词由平台或开发者预先写好，在对话开始前（甚至每一轮请求时）自动注入给模型，用户通常看不到。它定义的是模型的身份、语气、行为边界、输出格式与安全规则，相当于一份常驻的「宪法」。

  • 决定「你是谁」——扮演什么角色、用什么语气说话
  • 决定「守什么规矩」——能做什么、不能做什么

3. Skill（技能）

Skill 是把某类具体任务的流程、方法、模板打包成的可复用「技能包」，按需加载。当任务命中某个技能时，对应的详细指令才会被展开注入上下文。它采用「渐进式披露」的思路，避免把所有知识一股脑塞进系统提示词里，让模型又臃肿又慢。

  • 教模型「这类活怎么干得更好」
  • 可组合、可复用、按需加载

4. MCP（Model Context Protocol）

MCP 是一个开放协议，让模型能够连接外部的工具、数据源和资源（数据库、API、文件系统、浏览器等）。它解决的是「模型如何真正动手做事」，而不只是「说得好听」——通过 MCP Server 对外暴露 tools、resources、prompts，模型获得了可调用的「手脚」与「资料」。

四者的关系

把 AI 助手想象成一个人，就能很好理解这四者：

  • 系统提示词 = 他的「人设与职业操守」（常驻，决定他是谁、守什么规矩）
  • 提示词 = 你每次对他说的「具体任务」（每轮变化）
  • Skill = 他抽屉里的「操作手册」（需要时抽出来照着做）
  • MCP = 他手里的「工具箱 / 资料库」（让他能真正调用外部能力）

从「常驻 → 临时」的层次看：

  1. 系统提示词：最底层、常驻的基础规则
  2. Skill：中间层、按需加载的方法论
  3. 提示词：最外层、每一轮的具体任务
  4. MCP：横向贯穿，为以上三层提供工具与资源
一句话总结：
提示词告诉模型「做什么」；系统提示词告诉模型「你是谁、守什么规矩」；Skill 告诉模型「这类事怎么做」；MCP 让模型「能真正调用外部工具去做」。

对比一览

维度提示词系统提示词SkillMCP
来源用户每次输入平台 / 开发者预设开发者 / 用户打包工具提供方
生命周期单轮常驻按需加载连接期间
解决什么做什么我是谁 / 守规矩怎么做更好能调用什么

Skill 的标准格式

上面从概念层面讲清了 Skill 是什么，下面补充它的「落地标准」——一个技能文件夹应该长什么样、每个文件与字段分别承担什么职责。核心一句话：只有 SKILL.md 是必需的，三类资源按需增加；name 与 description 是技能的「身份与广告」，scripts / references / assets 各司其职。

标准目录结构

一个文件夹、一份入口文件、三类可选资源：

skill-name/
├── SKILL.md              ← 必需：唯一入口文件
│   ├── YAML frontmatter  ← 必需：name + description
│   └── Markdown 正文      ← 必需：怎么做
├── scripts/              ← 可选：可执行代码
├── references/           ← 可选：参考文档
└── assets/               ← 可选：输出素材

最小可用形态——一个文件就是一个技能：

skill-name/
└── SKILL.md

典型完整形态：

skill-name/
├── SKILL.md
├── scripts/              extract_pdf.py
├── references/           form-schema.md
└── assets/               report-template.docx

三条硬规则：

  1. 文件名必须精确为 SKILL.md（区分大小写）。
  2. 文件夹名必须与 frontmatter 的 name 一致。
  3. 文件名与目录名只用小写字母、数字、连字符。

存放位置与作用域：

  • 用户级 ~/.workbuddy/skills/：跟随你跨所有项目可用，适合个人工作流。
  • 项目级 <项目>/.workbuddy/skills/：随仓库提交、团队共享，适合团队约定。

选择建议：不确定时优先用用户级；只有确实需要团队共享（团队规范、项目专属模型、共享流程）时才建项目级。

SKILL.md 的 YAML frontmatter

开头的一段元数据，决定了技能的身份与可发现性：

---
name: pdf-processing
description: Extracts text and tables from
  PDF files, fills forms, and merges
  multiple PDFs. Use when working with
  PDF documents or when the user
  mentions PDFs, forms, or extraction.
license: MIT
allowed-tools: Bash(git:*) Read
metadata:
  author: your-name
  version: "1.0.0"
---
字段必需规则
name是≤ 64 字符；仅小写字母、数字、连字符
description是≤ 1024 字符；非空；第三人称；写清做什么 + 何时用
license否许可证名称，或随包分发的许可证文件名
allowed-tools否预授权工具列表，部分客户端支持
metadata否自定义键值对，如作者、版本

注意：frontmatter 里不要写 XML 标签；name 不能使用保留字（如 anthropic、claude 等）。

name 字段：命名规则

它是技能的唯一标识，也是目录名。

  • 只用小写字母、数字和连字符（hyphen-case）；最长 64 个字符。
  • 必须与所在文件夹名完全一致；不能包含 XML 标签，不能使用保留字。

推荐做法：用动名词或名词短语，一眼看出能力边界，同一套技能库内保持统一命名模式。合格的命名如 pdf-processing、cpp-ut-coverage-enhancer、generating-reports；不合格的如 PDF_Processing（含大写与下划线）、-pdf-tool（不能以连字符开头）、data--analysis（连续连字符）、helper / utils（语义空泛，无法判断能力边界）。

description 字段：最重要的一个字段

它决定技能能否被发现、能否被正确触发。写好它的公式：做什么（能力）+ 具体产物（对象与格式）+ 何时使用（触发场景与关键词）。

合格示例：Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction. → 能力清晰、产物明确、场景与关键词齐全。

不合格示例：Helps with PDFs. → 没说清能做什么、产出什么，也没给出任何触发线索，模型无从判断何时该用它。
  • 人称：一律第三人称，写 "Processes Excel files…"，不写 "I can help you…" / "You can use this to…"。
  • 长度：≤ 1024 字符，够用即可，不必写成长文。
  • 关键词：把用户真的会说的词写进去（俗称、中英文名、文件格式、常见动宾短语）。
  • 最易漏的一条：「何时用」比「做什么」更容易被漏掉，而它恰恰是触发匹配的主要依据。

SKILL.md 正文的标准结构

正文是「工作手册」，不是资料汇编。推荐的正文骨架：

  • # 技能名称
  • ## 概述：一段话说清这个技能解决什么问题
  • ## 使用场景：触发条件清单（什么情况下该用它）
  • ## 工作流程：编号步骤，核心部分，必须可执行
  • ## 资源引用：何时读哪个 reference / 跑哪个脚本
  • ## 约束与边界：Do NOT 清单，明确不做什么
  • ## 示例：一个完整的输入 → 输出范例

语言风格：用祈使句 / 不定式，客观、指令式。写 "To rotate a PDF, run scripts/…"，不写 "You should…" 或 "I can…"。

长度控制：正文控制在 500 行以内；超出就说明有细节该下沉到 references/ 或写进 scripts/，而不是继续加在正文里。

避免重复：同一信息只存一处。正文和 references 各写一份，改的时候必然漏掉一处，最终导致模型读到互相矛盾的说法。

一句话：正文只写「每一步都必须看到的流程与规则」，凡是「用到才查」的内容，都应该外移到捆绑资源里。

scripts/ —— 可执行代码

可执行代码：能交给机器做的，就不要交给模型每次现写。让确定性、可重复的操作变成「一行命令」，并且可以不读入上下文就直接执行。

  • 适合放什么：反复重写的同一段代码；需要确定性结果的计算、转换与批量处理；带参数校验和错误处理的一次性任务；需要调用外部命令或 API 的固定流程；生成产物需要严格格式控制的场景。
  • 写作标准：一个脚本只做一件事（单一职责）；文件头注释写清用途、参数与用法；错误处理显式且信息可读，不静默失败；路径统一用正斜杠 /，不出现 Windows 风格路径；不留「魔法常量」；依赖包在 SKILL.md 中列明并验证可用。

反模式：把大段代码直接内联在 SKILL.md 里——既挤占上下文，又无法复用与调试；正确做法是抽成脚本，正文里只写「何时运行它」。

references/ —— 参考文档

参考文档：给模型读的「背景资料」，用到才加载。存放「需要时才查」的详细信息，是保持 SKILL.md 精简的主要手段。

  • 适合放什么：数据库表结构、字段含义与关系说明；内部 API 文档、请求示例与返回格式；公司规范、政策文件、模板使用说明；长流程的详细指南与领域知识手册；需要大量表格、清单、枚举值的资料。
  • 写作标准：按主题拆成多个文件（如 api-guide.md、schema.md），不要堆成一个大文件；在 SKILL.md 中用一行说明「何时读哪一个」；大文件（> 10k 词）在正文里给出检索关键词；不与 SKILL.md 内容重复；引用深度只做一层，不要 A → B → C 链式跳转。

反模式：把整本规范粘进 SKILL.md 正文——正文应只留流程与判断，把可查、可枚举的长资料下沉到 references/，按需加载。

assets/ —— 输出素材

输出素材：不进上下文，只进产物。存放不进入上下文、而是直接用在最终产物里的文件，是技能与产出之间的桥梁。

  • 适合放什么：品牌资产（logo、字体、配色方案文件）；模板（PPT 模板、Word 模板、HTML 脚手架）；示例文件（样板文档、样例配置、图标集）；会被复制、填充或修改后交付的骨架文件；需要嵌入产物的静态资源。
  • 写作标准：只放「会进入交付物」的文件，不做资料囤积；与 references/ 区分——那边给模型看，这边给产物用；在 SKILL.md 中说明每个素材的用途与套用位置；保持素材为可二次编辑的原始格式；命名体现版本（如 brand-logo-v2.png）。

常见混淆：把「参考文档」放进 assets/，或把「模板」放进 references/。判断标准很简单——它会不会被复制进最终文件？会，就放 assets/。

该建哪个目录：判断标准

一句话归位，避免把东西放错地方：

你手上的东西是……放哪里原因
一段反复重写的代码scripts/可直接执行，结果确定，且不占用上下文
需要模型阅读理解的长文档references/按需加载进上下文，用完即走
要嵌入最终产物的模板、图片、字体assets/不进上下文，只作为产出素材被复制
几句核心流程说明与判断规则SKILL.md 正文这是技能的主干，必须常读
一个完整的输入 → 输出示范SKILL.md 正文 / references/短示范放正文，长示范放参考文档
判断口诀：能给机器执行的 → scripts/　需要模型阅读的 → references/　要被用在产物里的 → assets/　属于主干流程的 → SKILL.md 正文。
